0.1 原型与 PRD 分工

  • 原型页只展示 UI 与可点交互；业务规则、字段口径、验收要点以本 PRD为准（与报价组一致）。

  • 原型右下角/侧边「PRD」芯片可展开本文（ess-prototype-prd.js 嵌入）。

0.2 变更标记

  • NEW 本次新增能力或字段。
  • 改 相对现网查货操作的改动。
  • 待定 仅占位，不得作为开发验收口径。

0.3 UI 风格（对齐报价组原型）

  • 顶栏深色导航 + 左侧分组菜单；主区白底 panel、表头筛选 input、工具栏按钮分主次色。
  • 侧栏抽屉宽约 1120px，双列布局；弹窗居中，点击遮罩不关闭（须点「关闭/取消」），与报价组绑单/核对弹窗一致。
  • 操作结果用 toast；需通知业务/客服时用「双通道通知」浮层（企微 + 系统消息）。

0.4 批量 / 单票模式

核心区分：批量 = 把勾选的一批运单拉进产品确认操作台，本批处理完关闭；单票 = 每次只处理 1 票的查货 / 扣件 / 确认。两种模式下，操作台内的「确认并下一条」「扣件确定」始终按票执行，不存在一键确认整批。

模式含义勾选校验典型操作
批量（默认） 勾选的运单作为一批进入产品确认操作台；本批最后一条处理完自动关闭侧栏 产品确认 / +查货扣件：至少勾选 1 票（不支持无勾选自动入队）
添加费用 / 查货扣件放行：至少 1 票，可多票
批量添加附加服务：≥2 票；修改附加服务：恰好 1 票，或行「改附加」直接带出		 ① 勾选本批 →「产品确认」→ 操作台逐票确认或扣件
②「+ 添加费用」→ 费用弹窗带出勾选的运单列表（默认全选、可勾除）
单票 每次只处理 1 票：查货（识图）、扣件、确认 工具栏操作须恰好勾选 1 票，否则 toast 拦截 行「识图 / 加费用」直接处理当前票；或勾 1 票 → 产品确认 / 查货扣件
操作批量模式单票模式
产品确认勾选票 → 操作台队列 → 按票确认/扣件 → 本批完毕关闭勾 1 票 → 操作台处理该票 → 完毕关闭
+ 查货扣件勾选票 → 操作台 → 按票「扣件确定」勾 1 票 → 操作台扣件
+ 添加费用勾选票 → 弹窗运单列表（默认全选）勾 1 票 → 弹窗仅该票
批量添加附加服务勾选 ≥2 票 → 附加服务弹窗（多票回显/半选）不适用（须改用「修改附加服务」）
修改附加服务不适用（须 ≥2 票时用「批量添加」）勾 1 票，或行「改附加」直接带出当前票
行 · 识图 / 加费用 / 改附加不受模式切换影响，始终单票（浏览/带出当前行，非批量队列）

2.5 AI 自动识图（后台）

  • 仓库拍图上传成功 → 系统自动调用 AI，无需「触发识图」按钮。
  • 输入：图片、申报品名/品牌、是否侵权/带电等上下文（侧栏「喂给 AI」chips 同口径）。
  • 输出回写列表：AI识图、建议品名、识别品牌、是否侵权(AI)/带电、品名识别状态（通常 → 待人工确认）。各字段取值见 2.7 总表。

2.6.5 风险告知

  • 入口：产品确认侧栏「风险告知」区块勾选「涉及资质 · 快捷语」并执行确认/扣件 → 双通道通知成功后，本票 riskNotify →「已告知」。
  • 「添加费用」弹窗「附加费备注」使用独立词表 QUICK_FEE（21 条，见 8.3）；勾选后双通道通知；不回写「风险告知」列。
  • 列表「风险告知」列同步展示；列头筛选支持 已告知 / 未告知。
  • 与侵权状态独立：可先告知风险，后补授权附件。

2.6.6 与侧栏、报关衔接

  • 附件上传入口统一在侧栏「⑤ 附件」（保函 / 国内授权 / 国外授权），不在列表行内上传。
  • 上传后列表三列即时刷新；更换/清除文件名同步更新标记颜色。
  • 品牌授权书类型文件计划同步至报关管理「品牌授权比对」（授权主体 vs 报关抬头）；完整硬卡逻辑见待定项，列表仅展示上传有无。

3.6 典型作业流程

A · 批量产品确认（主路径）

  1. 列表保持批量，勾选本批待处理运单（至少 1 票）。
  2. 点「产品确认」→ 侧栏操作台打开，头部 确认队列 1 / N。
  3. 逐票：点查货图 → 核对 AI →「确认并下一条」或「扣件确定」（均按票，非整批一键）。
  4. 本批需统一加价：点「添加费用」→ 弹窗带出本批运单列表（默认全选）。
  5. 第 N 票处理完 → 侧栏自动关闭，toast「本批已全部确认完毕」。

B · 单票处理

  1. 列表切单票，或直接使用行「识图 / 加费用 / 改附加」（不受模式约束，始终单票）。
  2. 工具栏路径：勾选 1 票 →「产品确认」或「+ 查货扣件」→ 操作台处理该票 → 关闭。
  3. 勾 2 票点工具栏操作 → toast 拦截。

C · 边确认边扣件

  1. 「+ 查货扣件」入队（批量/单票规则同 A）。
  2. 侧栏勾扣件标记 + 可选快捷语 → 扣件确定 → 本票进查货扣件中 → 自动跳下一条。
  3. 正常票仍用确认并下一条放行到产品已确认。

7.5.2 企微私聊 · 收件人与「企微名称」

企微通道与站内系统消息并行发送；系统消息走账号/消息中心，不依赖企微名称。企微私聊须通过企业微信 API 指定接收人，接收人标识统一取员工管理字段，不得用员工昵称、姓名或工号代替。

项规则
数据来源 员工管理（现网 ERP 员工档案 / 花名册）维护字段 「企微名称」 — 即该员工在企业微信内的 userid / 账号标识（与企微通讯录一致）
推送对象 按本票运单关联人员解析，默认至少包含：业务员、客服（与现网查货通知口径一致）；批量操作时按各票分别推送或合并摘要（以实现为准，须保证对象可解析到员工档案）
取值步骤 ① 由运单取业务员/客服等岗位对应员工工号或档案主键 → ② 查员工管理该员工 → ③ 读企微名称 → ④ 调用企微发私聊
展示（原型/列表） 通知列表「企微推送」、双通道浮层收件人摘要：展示解析到的员工姓名 + 企微名称（或姓名，企微名称作 tech 字段）；原型可 mock，开发须接真实字段
未维护企微名称 该员工跳过企微私聊，系统消息仍写入；记录发送失败/待补发日志（可选告警）；不 fallback 到昵称/手机号
维护责任 HR/行政或各组在员工管理维护；查货模块只读，不提供手改企微名称入口
