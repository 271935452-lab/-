一、会议结论（摘要）

80% 完成
  • 已收敛 核准问题本质：把「客户下单资料」与「客户上传的报关资料」核对准；整个关务环节围绕报关资料全流程 + 信息核准。
  • 已收敛 双通道取数：① 我方识别客户报关资料附件；② 报关行在预录阶段回传客户报关资料的结构化文档。两路都可对下单资料做核准。
  • 待设计 核准工作台：统一「基准侧（下单）」与「报关侧（附件识别 / 预录结构化）」字段比对、差异处置、通过/退回。
  • 已收敛 改配三类场景：甩柜换船（同提单同柜·轨迹延续）／查验换船（换提单同柜·轨迹延续·手改提单船名航次）／查验换柜换船（全新提单·旧轨迹可覆盖·重装重出）。
  • 缺口 跨角色同步：改配后须同步客服、海外客服、仓库等，系统要有事件通知，避免改了无人知。
  • 已收敛 线下三表：仓位表（货量/订舱）→ 装柜表（预配终配+装柜信息+报关行）→ 海派跟踪表（装柜完成池，关务也用）；当前 Excel 共维，系统需三视图一体。
与现有系统关系：报关行对接已覆盖预录附件回传（#04）与人工审附件； 字段级结构化比对（#05）尚未对接——今日核准双通道正是补这条能力的业务依据。

三、核心：资料核准双通道（今日重点）

目标：客户下单资料（系统结构化：品名 / HS / 件数 / 毛重 / 金额 / 抬头 / 申报要素等） 与客户报关资料逐项核准，减少肉眼打开附件比对。

通道① · 我方识别客户报关附件

客户上传报关资料（PDF / 图片 / Excel 等）后，系统识别 / 解析附件，抽成结构化字段， 再与下单资料比对。适用于：尚未推报关行、或需在推送前先做一轮自检。

通道② · 报关行预录回传结构化

报关行在预录阶段，除预录单附件外，回传客户报关资料对应的结构性文档 / 字段； 系统直接用结构化结果与下单资料比对。适用于：已推报关行、走预录复审主链路。

3.1 核准对象（建议字段集）

#字段下单侧来源报关侧来源（双通道）不一致后果（业务）
1品名 / 货描运单 / 货物信息附件识别 或 预录结构化改单 / 查验风险
2HS / 商品编码报关件 / 客户填写同上退单、耽误截关
3件数 · 毛重 · 净重 · 体积下单 / 收货 / 磅单同上舱单不一致 → 改运抵
4金额 / 币制报关件同上预录退回
5报关抬头合约 / 装柜表进口商同上报不了关；改买单 / 用我司抬头
6申报要素客户报关件同上预录反复修改
7分单号系统按船司规则生成舱单 / 预录绑定必须与舱单一致，否则改运抵

3.2 两条通道的关系

  • 不是二选一：通道①偏「推送前自检」；通道②偏「预录复审主路径」。可先后叠加，也可单票只走其一。
  • 同一套差异面板：无论字段来自识别还是报关行回传，核准 UI 统一（基准=下单，对照=报关侧）。
  • 人工兜底保留：识别失败 / 结构化缺失时，仍可打开原附件人工审（现状 #04）。

四、线下三表：仓位表 → 装柜表 → 海派跟踪表（今日重点③）

当前主要靠 Excel 共同维护；看货量去群里要订舱数据再维护进来。 系统目标：同一业务对象的三视图 + 状态流转，而不是三套孤岛表。

表 定位 核心内容 / 动作 谁用 流入 / 流出
仓位表 订舱货量总览 按周看仓位；群里要订舱数据 → 维护进表；关联订舱/品名 共同维护（船务为主） → 扩成装柜表
装柜表 仓位基础上的排柜落地 预配 / 终配 / 待配；装柜地址、时间、扩展；发哪个报关行 船务 / 关务 / 资料 终配·待配 → 报关资料出口；装柜完成 → 跟踪表
海派跟踪表 装柜完成后的跟踪池 装柜完成的都放这里；关务也会用；承接换船/改配后的跟踪 关务 / 尾端·海外客服等 改配事件写回；轨迹延续或覆盖见第五节

4.1 装柜表驱动报关资料出口（毛）

  • 装柜表取终配或待配 → 进报关明细 → 下载报关资料（现只改名）→ 直接发报关行。
  • 发哪个报关行：看装柜表。
  • 主痛点仍是分单号（各船司规则不同）。

4.2 与另外两个重点的衔接

  • 资料核准：装柜表决定「推给谁、何时可出资料」；核准工作台决定「资料对不对」。
  • 改配三类：①② 轨迹在跟踪表延续；③ 重装重出要回写仓位/装柜并覆盖旧跟踪。

4.3 舱单 / AMS（同场口径）

  • AMS = 总数据，舱单 = 分数据；截单前提 AMS 已发；发晚改单费 40 美金；资料不全也要先发不完整数据。
  • 舱单：推代理=下载表格；推海管家=直推；同船名船次可批量。
  • 给码头 / 报关行 / 车队同一份数据，并与代理一致；改运抵约 150。

4.4 委托 · 抬头（易错 → 核准相关）

#易错点与核准的关系
1 无委托报不了关（客户自做；长期一年 / 逐票） 核准通过前建议校验委托状态
2 抬头未申报好 → 改买单 / 用我司抬头 抬头是核准必比字段；异常走兜底策略
系统落点建议：三表做成同一对象的三视图（状态：订舱中 → 预配/终配/待配 → 装柜完成·跟踪中）； 报关资料下载带出报关行、分单号校验、与舱单一致性校验。详见产出物《三表流程与页面设计》。

五、甩柜 / 查验换船 / 查验换柜（轨迹与同步 · 今日重点②）

统一原则：系统必须能区分场景类型，并决定轨迹是否延续 / 覆盖、 提单号·柜号·船名航次如何改、以及通知哪些角色。

场景 提单号 柜号 轨迹规则 系统关键操作
① 甩柜、换船 同一提单号 同一柜号 不拆分，直接延续 改船名航次等配船信息；轨迹挂在原提单/柜上继续走
② 查验、换船 不同提单号 同一柜号 不拆分，直接延续 与①的区别：须在「查验换船」入口手动改提单号 + 船名航次；轨迹按柜号延续到新提单
③ 查验换柜、换船 新提单号 新柜号 等同全新提单；原提单轨迹可删除（覆盖） 货物信息改提单号+柜号时：同步新旧配舱、可改运单，相当于重装重出；资料删掉重发；旧核准作废
① vs ② 一句话：都是「轨迹延续、不拆开」；差别在提单号是否变 —— ② 必须走查验换船手改提单号/船名航次；① 提单号柜号都不变，只换船。
③ 一句话：柜也换了 = 新生命线；旧轨迹可覆盖，系统按重装重出处理并重建下游资料。

5.1 跨角色同步（硬要求）

改了系统若不同步，客服 / 海外客服 / 仓库等会继续按旧提单柜号作业 —— 今日明确要在系统体现。

角色需要感知什么建议触达
资料员 / 关务 场景类型、新旧提单/柜、资料是否需重发、核准是否作废 任务 / 待办 + 单据角标
客服（运单客服） 提单号/柜号/船名航次变更、对客话术口径 站内消息 / 钉钉；运单时间线事件
海外客服 / 尾端客服 是否换船、换柜、ETA 变化、轨迹是否延续 同上；跟踪表可见变更标记
仓库 ③ 重装重出：装柜计划/柜号变更；①② 是否影响提柜安排 装柜表/仓位变更通知

5.2 与资料核准的衔接

  • 场景①②：轨迹延续；若仅换船/换提单号，核准字段多数可继承，但舱单/AMS/船名航次相关需重核。
  • 场景③：新旧单关联后旧核准作废，新单重跑双通道核准；报关资料删掉重发。

六、AN / AMS / ISF（承接昨日 · 今日增量）

  • 优先清关宝（约 5W 余额）；海关家用后再付，暂后用。
  • 清关表格仍走邮件。
  • 与核准关系：AMS/舱单数据一致性是「件数毛体等」核准通过后的下游硬约束。
