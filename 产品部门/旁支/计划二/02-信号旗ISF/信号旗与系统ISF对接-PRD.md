## 1. 需求理解

现有系统已经有提单、运单、柜、工单和海外对接工作台，但信号旗的 ISF 申报与跟单宝节点尚未形成统一的数据闭环。本期要把信号旗的两份接口能力接入现有系统：

1. 由现有系统准备并提交 ISF 申报数据，保存信号旗返回的 `isfNo` 和回执。
2. 接收信号旗 ISF 回执，更新申报状态，支持失败重试、取消、下载回执 PDF。
3. 通过跟单宝按主提单查询船期、柜状态、清关状态和事件轨迹，并回写提单/柜/运单视图。
4. 只有需要人工补资料、协同或异常处理时，才生成/关联工单；工单不替代 ISF 主流程。

## 2. 本次处理目标

- 目标：形成信号旗两份接口文档与本系统对象、流程、状态、权限和工单联动的统一需求口径。
- 输出模式：全角色可评审版，重点覆盖前后端联调契约和测试验收条件。
- 本期范围：ISF 授权、提交/取消、回执、回执文件、订单号查询；跟单宝查询、异步重试、轨迹回写；异常与工单联动。
- 本期不做：不重做信号旗业务规则；不把信号旗状态直接当作本系统所有运输状态；不虚构信号旗未提供的回调地址、数据库表或内部接口 URL。

## 3. 已确认信息

### 3.1 来自信号旗 ISF 接口文档

- `[已确认]` 先调用 `POST /open/auth` 获取 token；入参为 `appID`、`appSecret`、`hdAppId`。调试地址为 `http://newhuodai.t.baoguan001.com/open/auth`，正式地址为 `http://www.codeflagai.com/open/auth`。
- `[已确认]` 提交接口为 `POST /open/isfSubmit`，后续请求需携带 token 和时间戳参数 `timestramp`。
- `[已确认]` 取消通过 `sendType=cancel`，再次发送/取消时传入原 `isfNo`。
- `[已确认]` 支持 `ISF-10`、`ISF-5` 两类申报。ISF-10 必须包含 `IM、CN、BY、ST、SE、LG、CS、MF` 8 类参与方；ISF-5 必须包含 `ST、BKP`。
- `[已确认]` 参与方字段包括 `partyRole`、`partyName`、`partyId`、`partyIdType`、国家、州/省、城市、邮编、详细地址。
- `[已确认]` 货物和航运字段包括 `shipmentType`、`bondSource`、`bondHolderType`、外国卸货港/交货地名称和代码、`hsCodes`、`amsBlNo`、`masterBillNo`、`amsType=OB/BM`、ETA、美国卸货港、柜型、柜号、`entrytypecode`、`customerNo`、`note`、`isfOrderInfoList` 等。
- `[已确认]` 当 Bond 类型为 16 时，`BondReferenceNo`、`SuretyCode` 必填。
- `[已确认]` 成功响应为 `code=200`，返回信号旗 `isfNo`；失败为 `code=500`。
- `[已确认]` 失败重试规则：未返回 `isfNo` 时可以重新发送；已经返回 `isfNo` 时，再次发送必须携带原 `isfNo`，避免重复计费。
- `[已确认]` 信号旗会向我方回调地址推送回执；回调 `data` 为 RSA 加密，解密后包含 `isfNo`、`amsBlNo`、`masterBillNo`、`responseType.code`、`responseType.message`、`responseType.date`。
- `[已确认]` 可通过 `POST /open/downloadIsfFile` 下载 ISF 回执 PDF；可通过 `POST /open/queryIsfNo` 按 `amsBlNo` 查询信号旗 ISF 订单号。

### 3.2 来自信号旗跟单宝接口文档

- `[已确认]` 查询接口为 `POST /open/query/tracking/order`，正式地址为 `http://www.codeflagai.com/open/query/tracking/order`。
- `[已确认]` 查询入参为 token、`timestramp`、`masterBillNo`、`sign`，`importerName` 可选。
- `[已确认]` 首次查询可能返回“订单保存中，请稍后查看”，调用方需要异步重试/查询。
- `[已确认]` 返回内容包含船名、航次、起运港、卸货港、ETA/ETD/ATA/ATD、进口商、提单状态、清关状态、保税编号及目的港、柜号/柜型/柜状态、船司事件、分单信息和进出口事件轨迹。
- `[已确认]` 跟单宝状态码：`1 查询中`、`10 在途`、`20 已到港`、`30 查验中`、`40 已放行`、`50 预警`、`60 查询失败`。
- `[已确认]` `sign` 计算规则：请求参数加 token 绑定的 appID；按 key 字母升序；拼接 `key=value`；计算小写 32 位 MD5；sign 不能重复使用，时间戳超过 5 分钟失效。

- `[已确认]` 工单详情已有两类独立前置校验：运单状态限制、账单锁账/核销限制。

## 4. 业务边界与核心原则

### 4.1 责任边界

| 能力 | 主责角色/系统 | 本期系统行为 | 边界 |
| --- | --- | --- | --- |
| ISF 业务资料准备 | 关务/报关执行侧 | 维护必填字段、参与方、Bond、提单和货物资料 | `[待确认]` 现有系统的最终资料维护页面与责任人 |
| ISF 发送与取消 | 本系统对接服务 + 信号旗 | 按接口契约发送、记录结果、支持取消 | 不改变关务审批口径 |
| ISF 回执 | 信号旗 → 本系统 | 接收、解密、验签/去重后回写 | 回调地址和 RSA 密钥由双方确认 |
| 船期/柜轨迹 | 信号旗跟单宝 | 按主提单查询并回写 | 不覆盖本系统人工确认的实际节点 |
| 货物操作工单 | 工单模块、海外仓/客服 | 承接资料缺失、异常和人工协同 | 不替代 ISF 申报和船司节点主数据 |

### 4.2 数据优先级建议

- `[建议]` 信号旗返回的“外部状态/外部时间”作为外部来源展示，保留原值和抓取时间。
- `[建议]` 本系统已确认的实际节点（如人工确认 ATA、海外仓执行结果）不被跟单宝查询覆盖；发生冲突时并列显示并记录来源。
- `[待确认]` 若现有系统已有同名字段，需确定“信号旗外部值、现有系统值、人工覆盖值”的优先级和是否允许回滚。

## 5. 目标流程

### 5.1 ISF 首次发送

1. 关务/报关执行在现有提单或 ISF 页面选择“发送 ISF”。
2. 系统校验 `ISF-10/ISF-5` 参与方、提单号、AMS Bill No、Bond、港口和货物字段。
3. 校验通过后，系统获取/复用有效 token，生成一次性时间戳和请求日志。
4. 系统调用 `/open/isfSubmit`，成功则保存 `isfNo`，状态变为“已提交/待回执”。
5. 失败且无 `isfNo` 时允许按失败原因重试；失败但已有 `isfNo` 时必须带原 `isfNo` 重发。
6. 信号旗回调到我方地址后，系统解密并按 `isfNo + responseType.code + responseType.date` 去重，更新回执状态。
7. 用户可在详情下载回执 PDF；回执失败或资料缺失时，可一键转工单协同。

### 5.2 ISF 取消/换单重发

1. 仅允许在 `[待确认]` 的可取消状态下操作，页面展示取消原因并二次确认。
2. 调用 `/open/isfSubmit`，传 `sendType=cancel` 和原 `isfNo`。
3. 取消成功后，原申报标记为“已取消”，不可再覆盖原记录。
4. 换单重发建立新版本，关联原 `isfNo`、新 `masterBillNo/amsBlNo` 和变更原因；不得将新版本写回旧版本。

### 5.3 跟单宝查询与轨迹回写

1. 用户在提单/柜详情点击“查询信号旗跟单宝”，或由系统按配置定时查询。
2. 生成 5 分钟内有效且不可复用的 `timestramp`，按规则计算 `sign`。
3. 首次返回“订单保存中”时，订单状态为“查询中”，按 `[待确认]` 的重试间隔与次数异步重试。
4. 成功后保存船期、柜状态、清关状态和事件轨迹；原始报文保留用于追溯。
5. 返回 `30 查验中`、`50 预警`、`60 查询失败` 时，按规则生成提示；只有需要人工处理的情况才创建异常工单。
6. 后续查询采用增量合并：事件以外部事件 ID（若接口提供）或“事件类型+时间+柜号/提单号”去重；若接口未提供稳定 ID，需产品与研发确认去重键。

## 8. 状态设计

### 8.1 ISF 状态

`草稿` → `待发送` → `发送中` → `已提交/待回执` → `已接受` / `已拒绝` / `已取消` / `发送失败` / `回执超时`

- `[建议]` 外部 `responseType.code` 原码和文案必须原样保存，同时配置本系统归一化状态。
- `[待确认]` S1、S2、S3、S4、S5、S6、01、02 各自代表的中文业务状态需要由关务/信号旗双方确认后固化映射；未确认前仅展示“外部回执码 + 原文”。
- `[建议]` “发送失败”与“回执失败”分开统计，避免把网络失败误判为申报被拒。

### 8.2 跟单宝状态

## 9. 工单联动

### 9.1 触发场景

- ISF 必填资料缺失、中文名称/地址无法转换为英文：创建“ISF资料补充”工单，关联主单、AMS Bill No、ISF 版本。
- ISF 回执为拒绝/异常且需要人工处理：创建“ISF回执异常”工单，带外部码、原文、回执时间和回执 PDF。
- 跟单宝状态为预警、查询持续失败或事件长时间未更新：按 SLA 配置创建“信号旗跟踪异常”工单。
- 查验中仅作为外部状态展示；是否转为货物操作工单，须由业务规则或人工点击确认，避免重复建单。

### 9.2 工单字段补充

| 字段 | 说明 |
| --- | --- |
| 来源 | `ISF` / `跟单宝` |
| 外部订单号 | `isfNo` 或跟单宝查询批次号（如本系统生成） |
| 主单号 | `masterBillNo` |
| AMS Bill No | `amsBlNo` |
| 外部状态/回执码 | 原始码及中文解释 |
| 关联柜/运单/FBA | 按现有工单关联规则选填 |
| 附件 | 回执 PDF、失败报文摘要、人工补充资料 |
| 业务联动 | 仅在“财务/关务确认”后写回对应业务对象；不得由工单直接修改外部申报结果 |

### 9.3 与现有工单状态的关系

- 工单状态仍使用现有主线：发起 → 待接单 → 处理中 → 待协同 → 已结案。
- `[建议]` ISF/跟单宝外部状态作为工单的“业务状态快照”，不替换工单状态。
- 工单结案前必须填写处理结果；若已补资料并成功重发，记录新 `isfNo` 或回执结果；若外部仍失败，不能直接标记已结案。

## 11. 前端页面与交互

### 11.1 主单/ISF 详情

- 展示：ISF 类型、当前归一化状态、外部回执码/文案、`isfNo`、AMS Bill No、最近发送时间、最近回执时间、回执 PDF。
- 操作：发送、取消、重试、查询 ISF No、下载回执、查看原始回执、转工单。
- 发送前：按字段表逐项校验，错误定位到参与方和地址字段；中文名称/地址提示“请补充英文值”。
- 发送中：按钮禁用，显示处理中；刷新后以服务端状态为准，避免重复提交。
- 失败：区分“请求未成功”“信号旗已受理但回执失败”“资料校验失败”，提示下一步动作。

### 11.2 跟单宝查询卡片

- 展示查询状态码、船名/航次、港口、ETA/ETD/ATA/ATD、清关状态、柜状态、分单和事件时间线。
- “查询中”显示最近查询时间和下次重试时间；“查询失败”显示失败原因摘要与手动重试。
- 外部状态必须带来源标签“信号旗跟单宝”，不得与本系统实际节点混为一列。

### 11.3 工单入口

- 在 ISF 回执、跟单宝预警/持续失败卡片提供“转工单”。
- 自动带入主单、AMS Bill No、柜号、外部码、原文摘要和附件。
- 工单详情保留外部状态快照，后续外部状态变化以时间线追加，不覆盖历史处理记录。

## 14. 数据安全与合规

- appSecret、RSA 私钥、回调验签/解密材料不得进入前端、普通业务日志或导出文件。
- 原始请求/响应可能包含客户、地址、证件和货物信息，按现有敏感数据权限控制并设置留存周期 `[待确认]`。
- 页面默认脱敏展示证件号、客户敏感地址；具备相应字段权限时才可查看完整值。
- 发送前保留最终英文申报快照，后续主数据变化不反向修改已发送版本。

## 15. 历史兼容与迁移

- 已有主单、柜、运单和工单数据继续可查；新增外部状态、`isfNo`、回执和轨迹字段为空时显示“未对接/暂无数据”。
- 旧 ISF 记录若只有外部订单号，没有本系统版本号，导入时生成兼容版本并标记来源为“历史迁移”。
- 不回填无法确认来源的外部轨迹为本系统实际节点。
- 新旧规则并存期间，列表和详情均显示“数据来源”和“规则版本”。
- `[待确认]` 是否批量查询历史主单、历史回执 PDF 是否迁移、是否需要补建工单。

## 16. 验收标准（Given-When-Then）

### 正常

- **AC-001** Given 关务已填写 ISF-10 所需 8 类参与方且英文地址完整；When 点击发送；Then 系统调用 ISF 提交接口并保存 `isfNo`，状态显示“已提交/待回执”。
- **AC-002** Given 已保存 `isfNo` 的申报发送超时；When 用户重试；Then 请求必须带原 `isfNo`，不得创建无关联的新申报版本。
- **AC-003** Given 收到可解密的回执；When 系统处理回调；Then 保存回执码、原文、解密结果和时间，并更新对应 ISF 版本。
- **AC-004** Given 主单存在有效 `masterBillNo`；When 查询跟单宝；Then 显示船期、港口、柜状态、清关状态和轨迹，并带“信号旗跟单宝”来源。

### 边界

- **AC-005** Given ISF-10 缺少任一必需参与方；When 点击发送；Then 前端和服务端均拒绝请求，并定位缺失角色。
- **AC-006** Given Bond 类型为 16 且缺少 `BondReferenceNo` 或 `SuretyCode`；When 发送；Then 不调用外部接口，提示补齐字段。
- **AC-007** Given 参与方名称或地址只有中文；When 发送；Then 系统阻止发送并要求补充英文值，不得静默翻译后直接发送。
- **AC-008** Given 跟单宝首次返回“订单保存中”；When 查询完成；Then 状态保持“查询中”，按策略异步重试，不显示为失败。

### 错误/恢复

- **AC-009** Given 外部返回 `code=500` 且无 `isfNo`；When 用户重试；Then 允许重新发送并记录每次请求结果。
- **AC-010** Given 同一回调重复到达；When 系统处理第二次；Then 不重复更新业务状态、不重复建工单，但保留重复接收日志。
- **AC-011** Given 回调 RSA 解密失败；When 系统收到回调；Then 不修改 ISF 业务状态，创建技术异常记录并支持后续重放。
- **AC-012** Given 跟单宝连续查询失败达到阈值；When 系统执行升级；Then 创建信号旗跟踪异常工单，带主单号、失败次数和最近错误摘要。

### 权限/审计

- **AC-013** Given 船务用户无 ISF 发送权限；When 打开详情；Then 可查看授权范围内状态，但发送/取消按钮不可见或禁用，并有权限提示。
- **AC-014** Given 用户修改英文地址并发送；When 查看审计；Then 可看到修改前后值、操作人、时间和发送版本。
