# 工单流程共性与差异梳理

> 文档状态：需求草稿，可进入评审。  
> 主要读者：产品、业务、研发、测试。  
> 依据：`统一工单-状态流转-PRD.md`、`海外仓操作指令流程-系统设计草案.md`、本轮对话。  
> 最新结论：[已确认] 操作失败、审批拒绝、外部超时均保持当前状态；保存失败原因与尝试记录，按权限重试，不切换为独立失败状态。

## 1. 一句话结论

[建议] 系统不按每个场景配置一套可拖拽的完整状态流，而是使用统一状态骨架，并为每个操作配置“前置状态/业务条件/成功后置状态”。中间流程图只是由规则自动生成的预览。

统一工单的业务骨架是：**母工单持续协同，指令版本承载每一次有效要求，费用与外部执行是版本上的记录或阶段，不再拆成平级工单。**

## 2. 所有需生成工单场景的共性

| 编号 | 共性步骤/规则 | 适用口径 |
| --- | --- | --- |
| C-01 | 统一入口与来源留痕 | 从运单/异常页/柜子/货件发起，或补录企业微信指令；必须记录来源、发起人、时间和附件。 |
| C-02 | 先确定处理范围 | 带出单号、柜号、主/子单、货件、箱/件、客户、渠道和当前物流节点；明确整票还是部分货物。 |
| C-03 | 母工单 + 指令版本 | 同一在办业务对象收到新要求时，关联原母工单并新建 V2/V3；已下发、执行或完成的旧版本不可覆盖。 |
| C-04 | 前置条件校验 | 操作前校验版本当前状态、角色权限、必填资料、费用确认、需要时的审批/可行性/地址确认等条件。 |
| C-05 | 费用确认记录 | 每个版本均应存在“有费用已确认”或“无费用已确认”的预计费用确认记录；不能只靠发起页的费用预判放行。 |
| C-06 | 操作过程留痕 | 保存处理人、时间、外部单号或人工发送凭证、处理结果、附件和费用快照。 |
| C-07 | 结果确认后再回写 | 外部或人工操作完成不等于版本完成；业务/客服确认结果及实际费用（如有）后，才允许回写运单、柜子、货件等业务数据。 |
| C-08 | 回写可追溯 | 回写保存原值、新值、操作人、时间、指令版本和外部任务号；历史版本只读。 |
| C-09 | 失败不改业务状态 | 失败、拒绝、超时停留在当前状态；另存失败原因、失败时间、来源、重试次数和最近一次处理人，按权限重试/催办。 |
| C-10 | 母工单完成条件 | 仅当没有待处理版本、待费用确认、待回写事项，且货物已终结时，母工单才完成；否则保持处理中/持续跟进。 |

### 2.1 共用的状态驱动规则

```text
操作可执行 = 当前状态满足 + 必填资料齐全 + 当前角色有权限
          + 费用确认完成 +（按场景）可行性已确认 / 审批已通过 / 地址已确认

操作成功 = 写入该操作的成功后置状态 + 记录操作日志
操作失败 = 当前状态不变 + 记录异常尝试 + 提供重试/催办/人工处理入口
```

注意：前置状态必须注明所属对象，不能只写“待处理”。例如“费用已确认”属于费用记录，“海外仓已受理”属于外部执行记录，“待结果确认”属于指令版本。

## 3. 非共性：按场景变化的部分

| 差异维度 | 分支/适用场景 | 差异内容 |
| --- | --- | --- |
| 处理阶段 | 港前 | 以柜子计划/柜子数据 `Move Type=留仓` 和对应柜子备注登记为主；货物未到仓时不直接创建可执行外部任务，后续到仓再创建关联版本。 |
| 处理阶段 | 提柜后/已到海外仓 | 需要先确认是否可执行、是否已出库；可执行后再走仓内或外部操作。 |
| 审批 | 限时达快递提柜后拦截 | 海外仓确认可执行后，才需要部门经理审批。审批不是所有工单的必经步骤。 |
| 外部执行方式 | API 海外仓 | 下发接口，保存幂等键、请求/响应摘要和外部工单号。 |
| 外部执行方式 | 无接口海外仓 | 生成统一线下操作指令；由客服记录发送渠道、接收人和发送凭证。 |
| 外部执行方式 | 纯内部操作 | 不创建海外仓任务，例如部分内部字段处理；仍需满足该操作自身的前置条件和回写规则。 |
| 重出货物 | 卡派/偏仓改快递 | 需要腾信重出单号、制单员打单、面单地址/渠道确认，再创建海外仓操作指令。 |
| 拦截 | 港前快递/亚马逊拦截 | 记录留仓和柜子备注；提柜后还需确认实际是否拦截成功，不能在港前直接完结。 |
| 拦截 | 提柜后快递/亚马逊拦截 | 先做海外仓可行性确认；限时达场景额外审批；完成后回写拦截结论和最后货物位置。 |
| 拦截 | 港前私仓拦截 | 已知没有拦截费；仍建议生成“无费用确认”记录以满足统一版本审计。 |
| 换标 | 港前未到仓 | 留仓 + 柜子备注预置换标要求；原渠道不覆盖；到仓后继续处理。 |
| 换标 | 已到海外仓 | 需海外仓确认可执行；回传标签版本、照片和结果。 |
| 仓内操作 | 拍照、换箱、测量、打托、清点、销毁、撕标 | 主链路相同，差别主要在操作字段、费用项、结果数据和凭证类型。 |
| 结果/回写 | 不同操作类型 | 重出回写新运单号/面单；拦截回写货物位置/留仓；换标回写标签版本；仓内操作回写数量、尺寸、照片或证明。 |

## 4. 各场景最小流程对照

| 场景 | 共性主链路 | 仅本场景增加的节点/条件 | 成功回写重点 |
| --- | --- | --- | --- |
| 重出货物 | 发起 → 费用确认 → 执行 → 结果/实际费用确认 → 回写 | 腾信重出单号、制单打单、地址与面单确认 | 新运单号、新渠道、面单版本、地址确认 |
| 港前快递/亚马逊拦截 | 发起 → 费用确认 → 留仓登记 → 持续跟进 → 结果确认 | 柜子备注、`Move Type=留仓`、提柜后再次核实结果 | 留仓、拦截结论、最后货物位置 |
| 提柜后快递/亚马逊拦截 | 发起 → 可行性确认 →（限时达时审批）→ 费用确认 → 仓执行 → 回写 | 已出库判断；限时达经理审批 | 拦截成功/未成功、原因、货物位置 |
| 港前私仓拦截 | 发起 → 无费用确认 → 留仓登记 → 持续跟进 | 无拦截费；提柜后转私仓客服 | 留仓、后续处理人 |
| 提柜后私仓拦截 | 发起 → 可行性确认 → 费用确认 → 仓执行 → 回写 | 私仓受理与反馈 | 出库情况、拦截结果、凭证 |
| 换标 | 发起 → 费用确认 →（到仓时可行性确认）→ 仓执行 → 回写 | 港前为留仓/备注；到仓后为标签执行 | 标签版本、照片、无法执行原因 |
| 拍照/换箱/测量/打托/清点/销毁/撕标 | 发起 → 费用确认 →（到仓后）仓执行 → 回写 | 各自的作业参数和凭证 | 照片、尺寸、数量、差异、销毁证明等 |

## 5. 配置应当共用与应当拆分的内容

| 配置类别 | 应共用/固定 | 应按场景配置 |
| --- | --- | --- |
| 状态枚举 | 母工单、版本、外部执行、费用/回写四类状态的对象边界与含义 | 每个操作允许的前置状态、成功后置状态 |
| 失败处理 | 保持当前状态、留痕、重试、催办、权限校验 | 重试人、催办对象、最大重试次数、是否必须人工确认 |
| 费用 | “有费用/无费用均留确认记录”、实际加收需二次确认 | 费用项、报价来源、免收费条件、确认角色 |
| 审批 | 审批结果是可被前置条件引用的独立记录 | 哪些操作/渠道/阶段需要审批、审批链和阈值 |
| 外部执行 | 外部状态不直接完成版本；日志和外部单号必须保留 | API/人工方式、支持动作、字段映射、回调映射 |
| 回写 | 必须可追溯、旧版本不能覆盖 | 回写对象、字段、触发时机、失败后的人工处理 |
| SLA | 状态不因超时自动改变 | 场景时限、责任角色、催办/升级规则 |

## 6. 对页面设计的影响

[建议] 页面改为“操作状态配置”，不做管理员拖拽状态流：

1. 左侧：场景与操作列表，例如“提柜后快递拦截 / 下发海外仓”。
2. 中间：根据右侧规则自动生成只读链路预览。
3. 右侧：配置对象、允许前置状态、附加条件、成功后置状态、失败处理（固定为保持当前状态）、角色、SLA、回写目标。
4. 审批、费用、外部状态作为“附加条件/关联记录”，不要和指令版本状态混成一个枚举。

## 7. 状态与人员的配置方式

### 7.1 配置原则

[建议] 不在状态定义中直接配置某个具体员工；状态只配置**责任角色/工单池**、可执行动作和分派策略。具体人员是工单实例进入状态后，按分派规则从池中自动或人工认领得到。

```text
场景/口岸/阶段/产品/客户类型
            ↓（分派规则）
责任角色或工单池
            ↓（池内分配：轮询/认领/指定/当前处理人延续）
工单实例实际处理人
```

审批人不通过“状态负责人”配置：审批节点引用独立审批规则，例如“限时达 + 提柜后 + 拦截”命中部门经理审批链；审批通过只是某项操作的前置条件。

### 7.2 状态责任与动作权限矩阵

| 状态/阶段 | 默认责任角色/池 | 可执行动作的角色 | 实际人员产生方式 | 说明 |
| --- | --- | --- | --- | --- |
| 草稿 | 发起人 | 业务员、客服 | 固定为创建人；可转交有权限人员 | 仅保存/编辑，不进入执行。 |
| 待可行性确认 | 海外仓对接池 / 港后客服池 | 海外仓对接、港后客服 | 按海外仓、口岸、场景路由到池；池内认领或轮询 | 海外仓反馈是外部数据，内部跟进人仍为该池成员。 |
| 待经理审批 | 审批规则指定的审批人 | 审批人 | 审批引擎按组织、金额/时效阈值解析 | 不是客服池分派，也不应在状态页手填姓名。 |
| 待费用确认 | 业务/客服池 | 业务员、客服；需要时财务复核 | 默认回到发起人或来源业务；超时可转客服池 | “客户确认”是凭证/确认记录，不等于客户系统账号。 |
| 待执行准备 | 港前客服池 / 港后客服池 | 对应阶段客服 | 由港前/港后 + 口岸 + 场景分派 | 补齐资料、生成计划、确认附件。 |
| 待外部下发 / 待人工发送 | 港后客服池 / 海外仓对接池 | 港后客服、海外仓对接 | 按海外仓能力和口岸分派 | API 下发可由系统执行；人工发送必须有内部跟进人。 |
| 待海外仓受理 / 海外仓执行中 | 港后客服池（跟进） | 港后客服、海外仓对接 | 保持原处理人；离岗时回池重分配 | 海外仓不是本系统员工；它是外部执行方，系统只保存外部负责人/联系方式。 |
| 待结果与实际费用回传 | 港后客服池（跟进） | 港后客服、海外仓对接 | 保持当前跟进人或回池 | 负责催回结果、凭证和实际费用。 |
| 待实际费用确认 / 待结果确认 | 业务/客服池 | 业务员、客服；需要时财务 | 优先指回发起业务；无负责人时按客服池 | 业务确认结果后才允许回写。 |
| 回写中 | 系统 + 对应业务池 | 系统自动；有权限的客服/业务可重试 | 系统任务；失败后保留当前状态并生成待办给当前责任池 | 不能仅因回写失败把版本标完成。 |
| 版本已完成 / 母工单持续跟进 | 无固定处理人或母工单负责人 | 有权限人员新增后续版本 | 母工单可保留最后责任池/负责人供后续指令承接 | 终态版本只读；母工单是否完成另看货物终结条件。 |

### 7.3 每一条“状态—人员”配置应有的字段

| 字段 | 说明 |
| --- | --- |
| 适用范围 | 场景、港前/港后、口岸、海外仓、产品、客户类型等命中条件。 |
| 当前状态/操作 | 配置到具体操作，例如“待外部下发 → 发起人工发送”，不是笼统配置“港后工单”。 |
| 责任角色/池 | 引用角色编码或池 ID，不直接填员工姓名。 |
| 可操作角色 | 谁可确认、下发、回写、重试、转派；与责任池可不同。 |
| 分配策略 | 自动轮询、池内认领、指定人员、沿用当前处理人、回到发起人、系统任务。 |
| 兜底角色/池 | 当前池无人、人员离岗、数据不完整时转给谁。 |
| SLA 与升级对象 | 首响/处理时限、预警人、超时催办人；超时只加待办标记，不改变业务状态。 |
| 审批规则引用 | 可为空；有值时引用审批模板，而非直接配置负责人。 |
| 生效时间与审计 | 配置版本、操作人、变更前后值，防止历史工单的责任人被配置覆盖。 |

### 7.4 推荐的三层配置边界

1. **角色/工单池页**：维护成员、数据范围、菜单与操作权限，例如 `ROLE_GH_LA_PRIVATE`。
2. **分派规则页**：维护“口岸 + 港前/港后 + 场景 + 产品 + 客户类型 → 目标角色/池”。
3. **操作状态配置页**：维护“操作前置状态/条件 → 责任角色/池 → 成功后置状态 → 失败保持当前状态 + 重试与 SLA”。

这样同一角色可以被多个状态复用；同一状态也能因场景不同路由到不同池。角色成员变动只改角色页，不需要逐条修改状态规则。
