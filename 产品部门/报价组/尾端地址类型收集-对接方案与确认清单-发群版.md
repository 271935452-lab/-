**尾端地址类型收集项目 · 节前对齐 / 节后首场汇报对齐**

先说结论：这场项目最该先定的不是 AI，而是**地址数据怎么形成、谁维护、怎样可信地复用**。AI 只基于已留痕数据做摘要和提示，不自动改标签、不自动报价、不自动加费用。

**已对齐方向**
1. 询价/报价：报价员核实并登记地址类型  
2. 港后：客服登记实际派送结果（车型、尾板、额外费用、客户偏好等）  
3. 系统按收货地址沉淀，后续报价时提示历史收货条件与异常  
4. 规划节点：10/15 港后登记 → 10/20 地址库/提炼 → 10/30 报价推送验证  

**当前最大风险**  
10/15 若先做港后录入页，但**地址唯一规则、字段枚举、双层数据模型**未定，后续库表和 AI 会建在不可复用的自由文本上，返工成本高。

**建议两场会推进**

**第一场（目标与治理 · 建议节后第一天）**
1. 公司级目标与必要性：数据沉淀完整率、价值、呈现量规划（要可量化）  
2. 组织分工讲清楚（业务员 / 报价员 / 港后 / IT / 产品）  
3. 项目发起人与项目级别（按发起人级别定级）  
4. 里程碑与交付物共识（含 10/15、10/20、10/30）  
5. 是否设立项目指导委员会：按月看「收多少票、什么原因、美库及其他提拆数据」判断行不行  

**第二场（落地与激励）**
1. 具体动作与资源支持  
2. 各目标是否有序推进、如何保证完整交付  
3. 达成激励 / 未达成惩罚  
4. 配合方式：目标拆解到人、到量  
5. 量化对象先定清：等时费、车型、地址类型、预约（每票是否必查）等  

**会上必须拍板的 6 项输出**
1. 地址唯一匹配规则（不能只按地址文本）  
2. 地址类型 / 卸货条件 / 杂费 / 客户偏好的字段与枚举  
3. 「地址档案」与「单票实际记录」关系及更新规则（禁止最新一条直接覆盖历史）  
4. 业务员、报价员、港后的录入与修改权限（含谁改档案、谁纠错、要不要审）  
5. 第一期页面入口与端到端流程（含强制填写冲突的定案）  
6. AI 提示：展示位置、内容、人工纠错、验收标准（第一期只做历史摘要+风险提示）  

**强制填写冲突 · 建议定案（供会上确认）**  
- 业务员：可暂缺  
- 报价员提交报价前：必须选「已确认类型」或「暂无法确认」；选后者必须填原因  
→ 不阻塞询价，也不把空数据伪装成已确认  

**展示时点 · 建议定案**  
- 报价员审核地址时：先看历史提示（可修正）  
- 业务员收到报价时：同步看只读提示  
→ 同一套数据，不做两套推送逻辑  

**费用口径提醒**  
「历史发生过尾板/等时费」= 风险提示，≠ 本次必须收费。费用自动加价规则暂与数据沉淀拆开。

细节确认清单见同目录文档后半部分。请各位会前先过一遍枚举与权限表，节后第一场直接拍板。

## 一、项目一句话

把**收货地址**做成可复用主数据：报价前核实类型 → 港后回写实际派送 → 系统沉淀档案与单票事实 → 报价时提示历史条件与异常（AI 只做摘要，不做自动决策）。

---

## 二、双层数据模型（建议会上锁定）

| 对象 | 内容 | 更新方式 |
|------|------|----------|
| **地址档案** | 相对稳定：标准化地址、主地址类型、卸货能力、历史风险标签、分渠道迈数摘要 | 系统汇总 + 人工确认；保留来源/时间/运单/修改日志 |
| **单票实际记录** | 本票：实际车型、是否用尾板、杂费发生、异常、备注、预约情况 | 港后（及必要时报价）按运单追加，**不覆盖**档案历史 |

冲突示例：历史「无需尾板」，本票实际用了尾板 → 写入本票事实，并抬升档案「尾板风险」标签；**禁止**用最新一条直接改掉历史结论而不留痕。

## 三、P0 确认清单（请业务现场勾选）

### 1. 地址怎么唯一识别

**建议匹配键（标准化后）：**  
国家 + 州 + 城市 + 街道 + 门牌号 + 邮编 + Unit/Suite（可选 Place ID）

待确认：
- [ ] 是否采用上述标准化键？是否上 Google Place ID？  
- [ ] Unit/Suite 缺失时如何匹配（严格 / 降级到门牌+邮编）？  
- [ ] 历史脏数据谁清洗、是否允许人工合并地址？

### 2. 标准字段与枚举（材料未定义，必须补齐）

| 字段 | 待确认选项（示例，会上改） | 必填节点 | 备注 |
|------|---------------------------|----------|------|
| 地址类型 | 住宅 / 商业无卸货台 / 商业有卸货台 / 暂无法确认 | 报价提交前 | 与现有询价三选一对齐 |
| 需要尾板（要求） | 是 / 否 / 未知 | 报价或询价 | 与「实际使用」分开 |
| 实际使用尾板 | 是 / 否 | 港后出库 | 事实 |
| 车型-客户要求 | 枚举待定 | 可选 | |
| 车型-实际使用 | 26尺 / 53尺 / 其他待定 | 港后 | |
| 等时费 | 是否发生；或金额+币种+依据 | 港后 | 会上定粒度 |
| 超址费/预约费等 | 同上 | 港后 | |
| 客户偏好 | 自由文本 / 结构化标签 | 待定 | 建议标签+备注 |
| 迈数 | 系统测距 / 人工覆盖 | 报价 | 是否按海外仓分渠道 |
| 预约 | 是否每票必查 | 待定 | 天羽侧提到预约 |
| 照片 | 报价员上传 / 港后上传 | 待定 | 作核实依据 |

待确认口径：
- [ ] 「需要尾板」与「实际使用尾板」是否分字段？  
- [ ] 车型记客户要求、实际使用，还是两者都记？  
- [ ] 杂费记「是否发生」还是「金额+币种+计费依据」？  
- [ ] 客户偏好：标签枚举有哪些？

### 3. 三岗责任与权限

| 角色 | 职责 | 待确认 |
|------|------|--------|
| 业务员 | 提供地址与已知要求；可看只读历史提示；可补充说明 | 能否改档案？建议否 |
| 报价员 | 核实并维护**本票/询价**地址类型；可看历史提示并建议改档案 | 改档案是否要审？ |
| 港后客服 | 登记本票实际派送与异常；派送完成后标注 | 漏登能否出库？ |
| 档案管理员/主管 | 合并地址、纠正档案、处理争议 | 人选？ |

待确认：
- [ ] 谁能修改已沉淀地址档案？  
- [ ] 错误数据纠正流程与是否审核？  
- [ ] 报价员「必须核实」与业务「可暂不填」冲突是否按上文定案执行？

### 4. AI 边界（第一期）

**做：** 历史记录摘要 + 风险提示（依据、最近时间、关联运单数、置信状态、人工修正入口）  
**不做：** 自动改地址标签、自动报价、自动新增费用  

待确认：
- [ ] 展示位置：报价员审核时 + 业务员收报价只读 —— 是否同意？  
- [ ] 最少样本数 / 有效期 / 置信展示规则？  
- [ ] 验收标准谁签（指导委员会？）？

### 5. 第一期页面入口（与现网差距）

现有整柜尾端派送、尾端派送费页**尚未覆盖**本项目字段。第一期建议最小页面：

| 序号 | 页面 | 负责人侧 | 目标日期 |
|------|------|----------|----------|
| 1 | 港后·出库/派送完成登记（单票实际） | 港后 | 10/15 |
| 2 | 地址档案库 + 单票事实查询 | IT/产品 | 10/20 |
| 3 | 报价员·地址核实与历史提示 | 报价 | 10/30 |
| 4 | 业务员·报价只读提示 | 业务 | 10/30 |
| 5 | （可选）询价端历史提示卡 | 业务 | 视资源 |

待确认：
- [ ] 港后入口挂在哪个现网菜单？  
- [ ] 10/15 是否接受「先登记、后 AI」——AI 文案可晚于结构化沉淀？  
- [ ] 照片上传是否进 10/15？

## 四、量化目标建议（第二场拍板用 · 草案）

> 下列数字供会上改，避免只有口号。

| 指标 | 草案 | 统计口径 |
|------|------|----------|
| 港后应登记票完整率 | ≥ XX% | 派送完成票中必填字段齐全占比 |
| 报价前提交前地址确认率 | ≥ XX% | 「已确认」+「暂无法确认并填原因」 |
| 地址可匹配率 | ≥ XX% | 能归到唯一 addressId 的占比 |
| 美库 / 其他提拆分渠道票量与原因 | 月报 | 指导委员会评审输入 |
| 等时费/尾板发生票占比 | 月报 | 按仓、按渠道 |
| 预约核查执行率 | ≥ XX% | 若确定「每票必查」 |

激励/惩罚规则：由发起人与指导委员会在第二场定。
